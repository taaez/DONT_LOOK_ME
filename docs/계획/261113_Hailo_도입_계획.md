# 261113 Hailo(AI HAT+) 도입 계획 및 FPS·지연 목표

> 작성일: 2026-11-13 · 현재 상태와 측정값의 근거는 [261113 실험 결과](../실험결과/261113_기준선_및_main_vs_seok_비교.md) 참고
> 이 문서의 FPS와 지연 수치 중 **"추정"이라고 표시한 값은 Hailo 설치 후 실제로 측정해 확인해야 한다.**

## 한눈에 보기

| 항목 | 현재 (CPU) | **목표 (Hailo)** |
|---|---|---|
| 카메라 FPS | 15 | **30** |
| AI 처리 FPS | 6.4~7.1 | **30 이상 (카메라가 찍은 모든 프레임 처리)** |
| 건너뛴 카메라 프레임 | 52~58% | **0%** |
| 우리 장치가 더하는 지연 (촬영 → 디스플레이 표시) | 약 200~220ms | **100ms 이하 (p95 기준)** |
| 디스플레이 출력 FPS | 약 7 | **30** (Tapo 15FPS의 2배) |

**결론: "카메라 30FPS + Hailo로 매 프레임 처리(30FPS 이상)"를 목표로 한다.**
카메라 120FPS는 가능하지만 목표로 삼지 않는다 (3장 참고).

## 1. 우리 장치의 지연은 어디서 생기나

```
사람 움직임 → [① 카메라 촬영·전달] → [② AI 처리·마스킹] → [③ 디스플레이 표시]
          → (Tapo 홈캠이 디스플레이를 15FPS로 촬영 → Tapo 앱으로 전송)
```

| 구간 | 내용 | 현재 측정값 |
|---|---|---|
| ① 카메라 | 노출 → 센서 판독 → 이미지 처리 → 버퍼에서 대기 | 프레임 나이 중앙 **44ms** (15FPS) |
| ② 처리 | 전처리 + **추론** + 후처리 + 마스크 칠하기 + 출력 | **138~155ms** (추론이 130ms) |
| ③ 디스플레이 | 화면 갱신 주기 대기 + 패널 반응 | 약 15~25ms (60Hz 기준 추정, 미측정) |
| **합계** | | **약 200~220ms** |

**Tapo 쪽 지연은 우리 장치가 없어도 생긴다.** Tapo 홈캠은 원래도 15FPS로 촬영해서 앱으로 보낸다. 그래서 사용자가 "우리 장치 때문에 더 늦어졌다"고 느끼는 부분은 ①+②+③이다. 이 값을 **100ms 이하**로 만드는 것이 목표다(프로젝트 수정계획서 기준).

> 참고: 0.1초(100ms)는 사람이 "즉시 반응한다"고 느끼는 한계로 널리 쓰이는 기준이다. Tapo 앱 스트리밍 자체에도 지연이 있어서, 우리 장치가 100ms 이하만 더하면 사용자가 차이를 알아채기 어렵다. Tapo 앱의 실제 지연은 별도로 측정하지 않았다.

## 2. 카메라 FPS와 AI 처리 FPS 목표 계산

### 2.1 원칙
1. **AI 처리 FPS는 카메라 FPS 이상이어야 한다.** 그래야 건너뛰는 프레임이 없고, 버퍼에서 기다리는 시간도 줄어든다.
2. **처리량(FPS)과 지연(ms)은 다르다.** 30FPS를 내려면 각 단계가 33ms 안에 끝나야 한다. 반면 지연은 모든 단계를 **더한** 값이다. 단계를 동시에 돌리는 구조(파이프라인)로 만들면, 지연이 33ms보다 길어도 30FPS는 낼 수 있다.
3. **디스플레이 출력은 Tapo 15FPS의 2배(30FPS) 이상**이 좋다. 우리 출력이 15FPS이고 Tapo와 타이밍이 맞지 않으면, Tapo가 같은 화면을 두 번 찍거나 한 장을 건너뛰어 움직임이 끊겨 보인다. 출력이 30FPS면 Tapo가 찍는 순간마다 새 화면이 떠 있다. 이때 화면이 새로 바뀐 뒤 Tapo가 찍을 때까지 생기는 추가 지연은 최대 33ms다(15FPS 출력이면 최대 67ms).

### 2.2 설정별 예상 지연

①은 15FPS 측정값(프레임 간격의 약 0.66배)으로 비율을 계산했다. ②의 Hailo 처리 시간은 **추정**(추론 10~25ms + CPU 후처리·칠하기 10~15ms)이다.

| 설정 | ① 카메라 | ② 처리 | ③ 표시 | **합계** | 판정 |
|---|---|---|---|---|---|
| 현재: 카메라 15 + CPU 7FPS | 44 (측정) | 138~155 (측정) | 15~25 | **약 200~220ms** | ✗ |
| 카메라 15 + Hailo | 약 44 | 20~40 | 15~25 | 약 80~110ms | △ 경계선. 출력 15FPS라 Tapo와 끊김 |
| **카메라 30 + Hailo (목표)** | **약 22** | **20~40** | **15~25** | **약 60~90ms** | **○** |
| 카메라 60 + Hailo | 약 11 | 20~40 (60FPS 처리 필요) | 15~25 | 약 50~75ms | ○ 효과는 작고 위험이 큼 |
| 카메라 120 + Hailo | 약 6 | 120FPS 처리 불가능 수준 | 15~25 | — | ✗ |

### 2.3 최종 목표값

| 항목 | 목표 | 확인 방법 |
|---|---|---|
| 카메라 FPS | **30** | `analyze_log.py` [A]의 카메라 간격 33.3ms |
| AI 처리 FPS | **30 이상** (모든 프레임 처리) | [A] 건너뛴 카메라 프레임 **1% 미만** |
| 한 장당 처리 시간 (②) | **40ms 이하** (p95) | [B] 처리 합계 |
| 촬영 → 출력 지연 (①+②) | **75ms 이하** (p95) | [A] `latency_ms` |
| 촬영 → 화면 표시 (①+②+③) | **100ms 이하** (p95) | 아래 4.7의 실측 방법 |
| 노출 프레임 | CPU보다 많지 않을 것 → 최종 0 | `compare_methods.py` |

## 3. 카메라 120FPS를 목표로 하지 않는 이유

이 카메라는 640×480에서 최대 120FPS까지 찍을 수 있다(실측 120.1FPS). 그래도 목표로 삼지 않는 이유는 다음과 같다.

1. **나머지 단계가 따라가지 못한다.** 120FPS면 한 장당 8.3ms 안에 후처리, 칠하기, 출력이 모두 끝나야 한다. 마스크 칠하기만 지금 3~7ms다.
2. **어두운 곳에 약하다.** 노출이 최대 8.3ms로 제한된다. 밤의 집 안처럼 어두우면 화면이 어둡고 거칠어지고, 사람을 놓치는 원인이 된다.
3. **조명 깜빡임이 찍힐 수 있다.** 노출이 짧아지면 60Hz 조명의 깜빡임이 줄무늬나 밝기 변화로 찍힐 수 있다.
4. **출력 쪽이 쓰지 못한다.** 디스플레이는 보통 60Hz이고 Tapo는 15FPS다. 120장을 만들어도 대부분 버려진다.
5. **지연 개선 효과가 작다.** 30 → 120FPS로 올려도 ① 구간이 약 22ms → 6ms로 줄어들 뿐이다.

30FPS가 안정적으로 되면 60FPS를 **밝은 환경과 어두운 환경에서 모두** 시험해 보고 결정한다.

## 4. 진행 순서

### 4.1 준비
- **랜선이나 빠른 와이파이에서 진행한다.** 설치 용량이 수백 MB라 핫스팟은 비추천이다.
- `sudo` 비밀번호를 아는 사람이 진행한다.
- 지금 상태가 정상 동작하므로, 설치 전에 Pi 카드 백업을 권장한다(Raspberry Pi Imager의 이미지 백업 또는 다른 PC에서 카드 복제).

### 4.2 Hailo 소프트웨어 설치 (Pi 터미널)
```bash
sudo apt update && sudo apt full-upgrade -y
sudo apt install -y hailo-all
sudo reboot
```
설치 후 확인:
```bash
hailortcli fw-control identify     # "Device Architecture: HAILO8" 또는 "HAILO8L" 확인 (26 TOPS / 13 TOPS)
ls /dev/hailo0                     # 장치 파일이 있어야 함
cd ~/DONT_LOOK_ME && .venv/bin/python -c "import hailo_platform; print('OK')"   # venv에서 보이는지
```
- 지금 확인된 상태: PCIe에서 `Hailo-8 AI Processor`로 인식됨. 드라이버 미설치(`/dev/hailo0` 없음).
- 이 표시만으로는 Hailo-8(26 TOPS)인지 Hailo-8L(13 TOPS)인지 구분할 수 없다. `identify` 결과에 따라 **모델 파일(.hef)을 칩에 맞는 것으로 골라야 한다.**
- **PCIe Gen 3 설정:** 속도에 영향을 주므로 Raspberry Pi 공식 AI HAT+ 문서에서 필요 여부를 확인한다(`sudo raspi-config` → Advanced Options → PCIe Speed).

### 4.3 모델 준비와 순수 추론 속도 측정
```bash
ls /usr/share/hailo-models/        # hailo-all과 함께 설치되는 기본 모델 확인
hailortcli benchmark <모델>.hef     # 카메라 없이 칩 자체의 FPS와 지연 측정
```
- 기본 모델에 세그멘테이션 모델(예: yolov5n-seg 계열)이 있는지 확인한다. 없으면 **Hailo Model Zoo**에서 칩에 맞는 사전 변환 세그멘테이션 모델(.hef)을 받는다. 모두 COCO로 학습돼 있어 사람 클래스를 바로 쓸 수 있다.
- **.hef는 입력 크기가 고정이다** (예: 640×640). 크기를 바꾸거나 직접 학습한 모델을 쓰려면 x86 Ubuntu PC에서 Hailo Dataflow Compiler로 다시 변환해야 한다. 처음에는 Model Zoo 모델을 그대로 쓴다.
- **기록할 것:** 칩 종류, 모델 이름, 입력 크기, benchmark FPS와 지연.

### 4.4 공식 예제로 카메라 동작 확인
- Picamera2의 Hailo 예제(`picamera2` 저장소 `examples/hailo/`)나 Raspberry Pi와 Hailo가 제공하는 rpi5 예제에서 **세그멘테이션 예제**를 실행한다. 카메라 연동과 실제 FPS를 확인하는 단계다.
- 예제 구조(입력 크기 변환, 출력 텐서 형식, 후처리)를 4.5 구현에 참고한다.

### 4.5 우리 코드에 Hailo 실행 옵션 추가
- `person_mask.py`에 `--backend {cpu,hailo}`와 `--hef 경로` 옵션을 추가한다.
- Hailo 출력(박스, 마스크 계수, 프로토타입)을 사람 마스크로 바꾸는 후처리를 구현한다. 결과는 **지금과 같은 형태(사람 영역 합친 마스크)** 로 넘긴다. 그래야 `--log`, `analyze_log.py`, `compare_methods.py`, `--stream`, 녹화를 그대로 쓸 수 있다.
- 진단 로그의 단계별 시간에 **Hailo 추론 시간과 CPU 후처리 시간을 따로** 기록한다(어디가 병목인지 보기 위해).

### 4.6 30FPS를 위한 처리 구조 변경 (필요할 때)
- 지금 구조는 "읽기 → 추론 → 칠하기 → 출력"을 한 장씩 차례로 한다. Hailo 추론이 빨라도 나머지 합이 33ms를 넘으면 30FPS가 나오지 않는다.
- 필요하면 **카메라 읽기 / 추론(Hailo 비동기) / 칠하기·출력**을 별도 스레드로 나눈다. 단계 사이 대기열은 **최신 1장만** 보관한다. 쌓아 두면 지연이 계속 늘어난다.
- **마스크는 계속 같은 프레임의 결과만 쓴다.** 추론 결과를 다른 프레임에 칠하지 않는다.

### 4.7 측정과 검증
1. **속도:** 카메라 30FPS로 실시간 진단을 돌린다.
   ```bash
   python src/person_mask.py --source picamera --fps 30 --backend hailo --hef <모델>.hef \
       --no-show --stream 8000 --log runs/hailo_live.csv --save runs/hailo_live.mp4
   python tools/analyze_log.py runs/hailo_live.csv --plot runs/hailo_live.png
   ```
   2.3의 목표(처리 30FPS, 건너뛴 프레임 1% 미만, 지연 p95 75ms 이하)를 확인한다. 온도와 스로틀도 함께 본다.
2. **정확도:** Hailo는 모델을 8비트로 줄여서 돌리기 때문에 정확도가 CPU와 조금 다를 수 있다. 오늘 녹화한 `compare_raw.mp4`를 Hailo로 처리한 뒤 `compare_methods.py`로 **CPU `main`, `seok`과 노출 프레임을 비교**한다.
3. **실제 화면 지연 (①+②+③):** 핸드폰 슬로모션(240FPS)으로 **카메라 앞의 밀리초 타이머**와 **디스플레이에 나온 같은 타이머**를 한 화면에 같이 찍는다. 두 숫자의 차이가 실제 지연이다. 10번 이상 재서 중앙값과 최대값을 기록한다.
4. **어두운 환경:** 조명을 줄인 상태(밤 상황)에서 노출 시간, 검출률, 노출 프레임을 따로 측정한다.

### 4.8 놓친 프레임 대응 방식 다시 정하기
- 처리 FPS가 오르면 **같은 시간 동안 놓쳐도 프레임 수가 늘어난다.** 오늘 15FPS에서 3장(0.2초) 놓친 장면은 30FPS에서는 약 6장이 된다. `seok` 방식의 `--max-gap 3`은 **프레임 수 기준**이라, 30FPS에서는 이 장면을 보완하지 못하고 검은 보호 화면을 낸다. **대기 한도를 시간 기준(예: 0.2~0.3초)으로 바꿔야 한다.**
- 30FPS에서 `seok`식 보완의 지연 부담은 1장당 약 33ms다. 7장(0.23초)을 기다리면 보완 프레임만 약 230ms 늦어진다. 이 대기를 지연 목표에 포함할지 팀에서 정해야 한다.
- 지연 없이 막는 대안으로 **"직전 마스크 유지"** 가 있다. 사람이 사라지면 직전 마스크를 넓혀 짧은 시간 동안 함께 칠한다. 이 방식도 같은 원본으로 비교한다.
- 다음 비교 영상에는 **빈 방 구간, 들어오고 나가기, 가장자리 걸치기 반복**을 넣는다.

## 6. 위험 요소

| 위험 | 영향 | 대응 |
|---|---|---|
| 칩이 Hailo-8L(13 TOPS)이면 세그멘테이션 FPS가 낮을 수 있음 | 30FPS 미달 | 더 작은 모델과 입력 크기, 카메라 FPS를 실제 처리 FPS에 맞추기 |
| 세그멘테이션 후처리를 CPU가 함 | Hailo가 빨라도 CPU가 병목 | 단계별 시간 측정 후 후처리 최적화, 스레드 분리 |
| 8비트로 줄인 모델의 정확도 저하 | 노출 증가 | `compare_methods.py`로 CPU와 비교, 필요하면 conf와 dilate 조정 |
| .hef 입력 크기 고정 | imgsz 실험이 제한됨 | Model Zoo의 다른 크기 모델 사용, 필요하면 x86 PC에서 재변환 |
| 처리 FPS 상승 후 `seok` 대기 한도(프레임 수) 문제 | 검은 화면 증가 | 시간 기준 한도로 변경 |
| 발열 증가 | 클럭 저하 | 진단 로그의 온도·스로틀 확인, 쿨러 상태 점검 |
